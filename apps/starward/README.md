# STARWARD — ZSS autonomous starship

A standalone pixel-art starship management simulation inspired by the room-based clarity of FTL and the crew activity of Pixel Starships. The ship, crew and artwork are original.

## Play

Download **starward.html** from this folder using GitHub's **Download raw file** button. Open the downloaded HTML file in a current desktop browser. No installation, server, account, API key or network access is required. Downloading this branch as a ZIP also works: extract it and open apps/starward/starward.html.

This is a self-contained browser application, separate from Apollo's running services. It is not deployed as a hosted Site or registered in Apollo's sidebar.

On narrow screens the ship display scrolls horizontally. Room and destination buttons provide a keyboard-accessible alternative to clicking the canvas. A hosted URL would be needed for convenient play on phones.

## What is implemented

- Six departments and **16 stateful crew agents**, each with a persistent task claim, health, energy, food need, morale, skill and eight-entry task memory.
- Captain → executive officer → department heads → crew hierarchy. Captain directives affect task utility; department heads issue work with captain and order provenance.
- Crew physically walk across **15 rooms on three decks**, using connected corridors and two ladder shafts.
- Interior surveys reveal three initially unmapped compartments.
- Engineering plans **diagnose → fabricate → repair** dependencies. Scrap becomes parts; parts are spent on repairs. Each task reserves resources once when work starts, including after interruption.
- Medical staff treat injured agents in the medical bay. Critical patients leave duty; medical staff can stabilise themselves if both doctors are injured.
- Security patrols, handles unregistered drones, suppresses fires and checks overworked or stalled crew.
- Scientists survey sectors, analyse samples and develop five technologies. Engineering constructs unlocked maintenance drones, adaptive shields and hydroponics.
- Operations handles navigation, salvage, food and medical supplies. When a specialist department is lost or critically incapacitated, operations can fill the missing role at half work speed.
- Real simulated fires, hull breaches, injuries, security incidents and discoveries. Crew can pre-empt routine work for emergencies.
- Eight connected sectors, adjacent-sector jumps, limited fuel, local surveys and autonomous navigation.
- Captain priorities, room and crew inspectors, task ledger, progress bars, research archive, live communications, pause, three speeds, mission objective and failure state.
- Local autosave, portable JSON backup, validated restore and deterministic random-state continuation.

The expedition objective is to map all compartments, survey five sectors and develop three technologies. The simulation continues after success. Hull failure, depleted oxygen or loss of every crew member ends the mission.

## Agent model

These are autonomous **rule-based simulation agents**, not independently running LLMs. The captain's director creates and reprioritises departmental jobs. Each available crew agent chooses a compatible task using priority, mission focus, travel distance and role suitability. Exclusive task claims prevent two agents from owning the same job. Prerequisites and material checks gate work; safety needs can release and requeue an interrupted task.

The executive officer is represented in the command hierarchy and coordination state. Departmental decisions currently share one director loop; this prototype does not claim separate model reasoning for the captain, XO or each department head.

Research findings are game data generated by completed surveys and experiments. This version does not browse real scientific sources, generate arbitrary code, design novel room layouts or construct arbitrary user-described devices. New equipment is built from the included research blueprints. Nothing controls physical equipment or spends real money.

## Controls

| Control | Behaviour |
| --- | --- |
| Captain directive | Prioritise exploration, restoration, science or crew welfare |
| Autonomous navigation | Let the captain choose adjacent destinations after surveys, when safe |
| Room or crew selection | Inspect condition, needs, provenance and active work |
| Sector selection | Inspect a destination and commission an adjacent-sector jump |
| Science tab | Follow research and commission available blueprints |
| Orders tab | Inspect live tasks, dependencies, issuers, assignees and logs |
| Trigger incident | Introduce a simulated incident for observation |
| Space | Pause or resume |
| 1 / 2 / 5 | Simulation speed |
| M | Switch ship / map |
| Save voyage / Load | Export or restore a portable JSON save |
| Guide | Open the in-game guide; the simulation pauses while it is open |

Time advances while the page is active; there is no off-page or closed-tab simulation. Autosave is local to the browser/device and may be unavailable in restricted or private browsing. The Save voyage button remains a portable backup option. Starting a new voyage asks for confirmation before replacing that device's autosave.

## Verification

The exact embedded engine was executed in the hosted JavaScript runtime:

- **21 simulation tests passed**, including hierarchy, all-room path connectivity, repair prerequisites, one-time resource reservation, sustained medical treatment, critically injured doctors, replacement-role coverage, emergency pre-emption, zero-material recovery, meals/rest, research locks, jumps, pause, command succession, deterministic save/resume, malformed saves and mission failure.
- Three seeded **40-minute simulated voyages** retained all 16 crew, surveyed all eight sectors, completed all five technologies and constructed all three equipment upgrades. Resources remained nonnegative; task, log and agent memory bounds held.
- Both embedded scripts compiled. UI startup and all room, crew, sector and tab render paths were smoke checked against a minimal DOM/canvas stub, including guide, save, incidents and animation frame stepping.

**Not verified:** real browser rendering, real pointer/touch interaction, keyboard focus with assistive technology, desktop file downloads, actual localStorage durability, Node execution of the packaged test runner, or hosted deployment. The stub smoke test is not browser QA.

To rerun the packaged engine suite with Node.js 18 or newer:

    node apps/starward/test-sim.cjs

Only Node built-in modules are used. The runner extracts the engine directly from starward.html so tests exercise the shipped application code.

## Source layout

| File | Role |
| --- | --- |
| starward.html | Complete game, CSS, procedural pixel art, engine and interface |
| test-sim.cjs | Dependency-free engine tests and script syntax checks |
| README.md | Run instructions, behaviour and verification limits |

The engine and interface occupy separate script blocks in the single HTML file so the game remains portable while the engine can be tested independently. Saves contain only game state. Imported identities, numeric ranges, room paths, task dependencies and ownership are checked before restoration; unrelated imported keys are discarded.
