# Apollo Practice Mode and grounded chat research

Practice extends Learning Missions with a local study loop. It does not replace the language model, train weights, prove understanding, or automatically modify Apollo's software.

## Start and control

Open Chat → Apps → **Practice & learning** (Learning Missions). Enter a public research topic, enable **Practice mode**, choose an existing knowledge node or leave automatic routing enabled, and authorise public research. The selected local Ollama model must be available. Training and Memory Bank must be enabled with their existing capabilities permitted in Core Services.

Chat commands (Tools enabled, normal persistent chat):

- `start public practice on retrieval methods until I say stop`
- `start public practice on retrieval methods until I say stop in node 42`
- `status practice 1`
- `pause practice 1`
- `resume practice 1`
- `stop practice 1`
- `stop practice mode` stops the single active learning/practice mission; if multiple are active, specify its ID.

Only the newest real user message or owner UI starts a mission. Model output, source text and tool JSON cannot authorise one. Temporary chat cannot start missions. Pausing prevents new batches; stopping finishes the current batch, retains evidence, writes a closing report and never resumes that mission automatically. Active missions resume on an enabled Apollo launch; Apollo must be running for work to proceed. Closing the app does not run work in the background while the PC/app is off.

## One practice cycle

1. Fetch up to three public pages using Training's existing web permissions. Save original source receipts.
2. Ask the configured local model for a small lesson with exact supporting source quotations, uncertainties and a next question. Reject claims whose quote is missing from the fetched page text. Matching a quote establishes provenance only; a source or its paraphrase may still be wrong.
3. Construct cloze questions from quotations. A fresh model conversation attempts the missing words without the answer key. Grade by exact case-insensitive word match, not model self-grading. This narrow score measures word recall, not semantic understanding.
4. Keep results, failures and next gaps in the shared SQLite mission database. Weak recall concepts or the next proposed gap guide the following bounded query, anchored to the original topic and rotating research focus.
5. Index new source-linked notes as **unverified research** in Memory Bank. Existing graph recall makes relevant notes available in later chats when Memory is enabled.

Automatic routing is **Research → the mission's topic**. A selected knowledge node adds explicit membership there; the memory's research type still keeps it in Research. Personal facts/preferences are not inferred. Sources and quotes remain in each memory. An indexing failure is visible in the mission inspector and retried after five minutes, including after restart. Stable mission/batch identifiers make a retry update the same memory. A repeated source/quote combination does not create another memory.

## Limits and recovery

- Existing budget: at most 24 research batches per mission per UTC day, then resume at the next UTC day. The UI shows scheduling state; this is not an unrestricted compute loop.
- Interval: 30–3600 seconds. Each practice batch uses up to two local model calls with a shared 120-second deadline.
- Localhost Ollama only; cloud-labelled models and external server addresses are rejected. No private memory or previous chat is supplied to practice generation.
- Three passes without new quoted evidence trigger an hour's backoff in continuous practice, then revisit the topic. Three practice errors or three research failures block the mission with the actual error.
- SQLite leases prevent two research workers from committing the same batch. Late/stale results cannot write lessons or memory. Source files, practice records and pending memory receipts survive ordinary restarts.
- No code execution, software installation, purchases, production changes or physical control occurs in this loop.

## Chat research modes

**Web research** now executes a bounded Training search/page-fetch batch before synthesising an answer. **Deep research** runs up to three batches (main question, primary evidence/limitations, and conflicting/recent evidence), with up to two pages per batch. Stop prevents later passes and generation at the next boundary. A current web fetch can finish first.

Readable sources are deduplicated, supplied as bounded untrusted excerpts to the model, and recorded in the response's Sources inspector and persisted metadata. Failed passes are reported to synthesis; if no readable page is fetched, the turn fails visibly instead of silently answering from model memory. A short scoped conversation is retained for local synthesis but is not sent as a public search query. Citation wording is generated by the installed model and should be checked against the recorded sources.

## Validation boundary

Automated tests exercise source matching, exact recall scoring, migrations, topic routing with a real SQLite Memory Bank, duplicate suppression, durable retry, pause/stop/restart behaviour, research permission failures, cancellation boundaries, worker routing and real Qt controls. They use deterministic source/model fixtures; they do not benchmark the quality of an installed Ollama model or establish ChatGPT feature parity.
